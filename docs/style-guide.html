ポートフォリオ デザインシステム

設計書 §2 の定義を実際の見た目で確認するためのスタイルガイド。このページ自体がサイトのアプリシェル（左サイドバー + 固定ヘッダー + 単一カラム）で組まれているので、読むこと自体が管理画面UIのプレビューになっている。

Next.js App Router Tailwind CSS v4 shadcn/ui Inter + Noto Sans JP

ヘッダーの Accent / Radius / Dark はこのページ全体に即反映される。決めた値はページ下部「トークン出力」に自動で反映されるので、そのまま globals.css に貼れる。

01

デザイン原則

迷ったときの判断基準。新しいUIを足すときは、まずこの3つに照らして考える。

Calm & Dense

管理画面らしい情報密度を保つ。階層は装飾ではなく、整列・余白・タイポの差でつくる。

Monochrome first

色は意味を持つときだけ使う。彩色するのはプライマリアクションのみで、それ以外はニュートラルの濃淡で表現する。

Motion is opt-in

アニメーションは状態変化の理解を助けるときだけ。ページ遷移演出は付けない。

02

カラー

ニュートラル1系統 + アクセント1色。shadcn/ui の CSS 変数規約に合わせ、すべて HSL のチャンネル値で保持する（hsl(var(--primary)) で参照）。

ニュートラルの選定

Zinc採用
Slate青みが強い
Stone暖色寄り

純グレーは無機質に見えやすいので、わずかに寒色へ振った Zinc を採用。青系のアクセントと同じ色温度でまとまり、白背景でも紙のような濁りが出ない。暖色アクセント（オレンジ）を選ぶ場合は Stone に変えると調和する。

セマンティックトークン

トークン用途LightDark

アクセントの候補

プライマリボタンの文字コントラスト — —

ボタン上の文字は白（--primary-foreground）。WCAG AA の本文基準は 4.5:1、ボタンのような大きめ・太めの文字は 3:1 が下限。ダークテーマでは同じ色相のまま明度を上げた値を使う。

使いどころのルール

Primary を使う
  • 各ページに1つだけの主アクション（お問い合わせ・送信）
  • 現在地を示すナビのインジケータ
  • フォーカスリング
Primary を使わない
  • 本文中のリンク（下線 + foreground で表現）
  • カテゴリバッジ・タグ（muted で表現）
  • 見出しの装飾、アイコンの着色

記事UI

Notion のブックマークDB（Design / Develop / Other の3つ）を表示する部分。リストとカードを切り替えられ、行やカードをクリックすると Notion ページ本文をモーダルで開く。

カテゴリ（design / develop / other）はプロパティではなくDBの分かれ方そのもの。3つのDB IDを環境変数で持ち、取得時にカテゴリを付与してマージする。タグの語彙はDBごとに異なるので、絞り込みチップは選択中カテゴリのタグだけを出す。

ツールバー — 絞り込みと表示切替

リスト表示 — 情報量を優先

リストが既定。1行に タイトル・概要・種別・タグ・ドメイン・日付 まで載るので、ストックを探すときはこちらが速い。カードはサムネイルで思い出したいときに切り替える。選択状態は ?view=card としてURLに持たせ、リロードしても保たれるようにする。

10
リソース運用

        
参考にする外部リソースを、どう使うかで3つに分類する。全部をそのまま取り込むとトンマナが崩れるので、コードを持ち込んでよい範囲を先に決めておく。


        

          
体験は借りる、トンマナは自前。

          
優れたコンポーネントを見つけたら、何が起きるか・どういう順序で起きるかだけを抜き出して、見た目は §2 のトークンで組み直す。デザインを丸ごとコピーしない。

        


        
3つの区分

        

          

            

              A
              そのまま入れる
            

            
shadcnと同じCSS変数を参照するもの。コピーした瞬間に自分のトークンに従うので、見た目が勝手に揃う。

          

          

            

              B
              体験だけ借りる
            

            
挙動は優れているが、独自の色・モーション・基盤を持つもの。コードは持ち込まず、インタラクションだけ真似て自前で組む。

          

          

            

              C
              判断基準として読ませる
            

            
コードではなく観点を提供するもの。実装後のレビューでエージェントに渡す。常時コンテキストには載せない。

持ち込み前の3つの確認

        

          
    
            
  1. 
              1
              
    
                
    色は hsl(var(--*)) で書かれているか？
    
                
    生の hex / oklch / Tailwind のカラークラス（bg-blue-500 等）が入っていたら、トークンに置き換えてから入れる。置き換えが大仕事ならコードを捨てて自前で組む。
    
              
    
            
    2. 
            
  2. 
              2
              
    
                
    独自の角丸・影・フォントを持ち込んでいないか？
    
                
    角丸は --radius からの相対値、影は --shadow-sm / --shadow の2段階だけ。ここが揃っていないと1コンポーネントだけ浮く。
    
              
    
            
    3. 
            
  3. 
              3
              
    
                
    依存パッケージが増えるか？
    
                
    増えるなら、その1コンポーネントのために入れる価値があるか考える。Motion を1箇所のために入れるのは割に合わないことが多い。
    
              
    
            
    4. 
          

        


        
使わないもの

        

          

            
            

              
reicon.dev

              
lucide と役割が完全に重複する。アイコンセットを2つ混ぜるのがトンマナ崩壊の最短ルートなので採用しない。lucide に欲しい形が無かったときの避難先としてだけ記憶しておく。

            

          

          

            
            

              
rareui の装飾系コンポーネント

              
Fluid Orb / Gravity Letters のような見せ場コンポーネントは、白黒の管理画面トンマナと正面衝突する。「かっこいいから」で入ったモーションは §2 の Motion is opt-in 違反としてレビューで落とす。
